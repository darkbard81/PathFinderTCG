# Pathfinder TCG 개발 로드맵

## 1. 문서 목적

이 문서는 현재 Pathfinder TCG 저장소를 실제로 플레이 가능한 싱글플레이 TCG로 확장하기 위한
단계별 구현 로드맵이다. 카드 규칙, 저장 데이터, 서버, 이미지 자산, Phaser/rexUI 화면을 서로
분리해서 진행하며, 각 단계는 다음 단계가 의존할 수 있는 검증된 산출물을 남긴다.

이 문서는 구현 완료 보고서가 아니다. 각 Phase의 `Done when`을 모두 만족한 경우에만 해당
기능이 완료된 것으로 본다.

### 공통 단계 정의 형식

모든 Phase는 아래 네 질문에 답해야 한다.

| 항목          | 질문                                         |
| ------------- | -------------------------------------------- |
| `Goal`        | 무엇을 만들거나 변경해야 하는가?             |
| `Context`     | 어떤 파일·오류·문서·기존 구현을 봐야 하는가? |
| `Constraints` | 무엇을 지키고 무엇을 변경하면 안 되는가?     |
| `Done when`   | 어떤 검증을 통과해야 완료인가?               |

## 2. 현재 기준

- `src/game/cards/GAME_DESIGN.md`의 코어 덱 검증 계약은 Phase 0에서 리더 1장과 유닛 29장,
  총 30장으로 확정되었다.
- `src/game/cards/card.d.ts`와 `card.schema.json`은 카드 정의용 선언 계약이고, Phase 1의
  직렬화 데이터 계약·Schema·validator는 `src/game/data/`에 구현되었다. Phase 3의
  `src/game/content/`에는 아군·적군 32종과 양쪽 30장 테스트 덱 구성이 구현되었다. Action 해결
  전투 런타임은 아직 구현되어 있지 않다.
- `src/game/simulation/GameSession.ts`는 starter 입력 상태만 소유하며 카드 전투 상태를
  처리하지 않는다.
- Phase 2의 `src/server/`에 로컬 계정, 고정 7일 세션, SQLite와 계정별 세이브 슬롯 API가
  구현되었다. Phase 3에서 실제 아군 starter 카드 30장과 덱을 새 슬롯에 주입하며, 로그인·슬롯
  화면은 Phase 7 범위다.
- 현재 시작 화면은 rexUI 커스텀 컴포넌트 쇼케이스이며 로그인, 세이브 슬롯, Stage, 덱 구성,
  전투 화면은 없다.
- 런타임 자산은 `public/assets/`에 두고, 게임 코드는
  `src/game/assets/manifest.ts`의 안정적인 자산 키를 사용한다.
- 시스템 Pillow와 프로젝트의 Sharp를 사용할 수 있다. Pillow는 픽셀·채널·마스크·투명도
  검증에, Sharp는 크기 정규화·합성·WebP 변환에 사용한다.
- `GAME_DESIGN.md` 22.1의 반응 피해 대상은 상대 리더가 아니라 기본 전투에서 피해를 준
  공격 카드인 `TRIGGER_SOURCE`다. 이후 시뮬레이션도 이 의미를 유지해야 한다.

### 게이트 A — 서버, 인증, 세션과 SQLite

#### 패키지와 실행 환경

- Node.js는 현재 저장소 계약인 `>=20.19.0`을 유지한다.
- 런타임 의존성은 Fastify `5.x`, `@fastify/cookie` `10.x`,
  `@fastify/rate-limit` `10.x`, `better-sqlite3` `12.x`를 사용한다.
- 비밀번호 해시는 별도 패키지 대신 `node:crypto.scrypt`를 사용한다.
- 개발 의존성은 TypeScript 서버 실행용 `tsx`와 SQLite 타입용
  `@types/better-sqlite3`만 추가한다.
- 설치 시 승인된 major 범위 안의 호환 버전을 선택하고 `package-lock.json`에 정확한 버전을
  고정한다. 다른 서버, 인증 또는 DB 패키지로 전환하려면 게이트 A를 재승인한다.

선정 근거는 Fastify의
[v5 Node.js 지원 기준](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/),
[`@fastify/cookie` 호환표](https://github.com/fastify/fastify-cookie),
[`@fastify/rate-limit` 호환표](https://github.com/fastify/fastify-rate-limit),
[`better-sqlite3` 기능과 WAL 권고](https://github.com/WiseLibs/better-sqlite3)다.

#### 계정과 비밀번호

- 사용자명은 앞뒤 공백을 제거하고 소문자로 정규화한 뒤
  `^[a-z0-9_-]{3,24}$`를 만족해야 한다.
- 비밀번호 길이는 12~128자로 제한하고 원문을 DB, 로그 또는 응답에 저장하지 않는다.
- 비밀번호마다 16바이트 무작위 salt를 만들고 `scrypt`의 `N=32768`, `r=8`, `p=1`,
  `maxmem=67108864`로 64바이트 해시를 저장한다. 64MiB `maxmem`은 현재 Node.js의 기본
  메모리 한도에서 이 파라미터가 거부되지 않도록 명시한다.

#### 세션과 요청 제한

- 세션 토큰은 암호학적 난수 32바이트로 만들고 클라이언트에는 원문을 한 번 전달하되 DB에는
  SHA-256 digest만 저장한다.
- 세션 만료는 생성 시점부터 고정 7일이며 사용 중 자동 연장하지 않는다.
- 쿠키 이름은 `ptcg_session`이며 `HttpOnly`, `SameSite=Lax`, `Path=/`를 사용한다. production
  HTTPS에서는 `Secure`를 반드시 활성화한다.
- 가입과 로그인은 IP와 정규화된 사용자명 조합당 10분에 10회로 제한한다.

#### 포트와 데이터베이스

- 개발 API는 `127.0.0.1:3011`에서 실행하고 현재 `3010` Vite 서버가 `/api`를 proxy한다.
- 배포 환경은 명시적인 `HOST`와 `PORT` 환경 변수로 bind 주소를 주입하며 소스에 외부 주소를
  하드코딩하지 않는다.
- 개발 DB는 `data/pathfinder-tcg.sqlite`, 테스트 DB는 테스트별 임시 경로를 사용한다.
- 연결 시 `foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout=5000`을 적용한다.
- Phase 2에서 로컬 `data/`를 Git ignore 대상으로 추가하고 실제 DB 파일을 커밋하지 않는다.

### 게이트 D — Stage 01, AI와 승리 보상

#### Stage와 AI 결정성

- Stage ID는 `stage-01`로 고정한다.
- 플레이어가 먼저 행동하고 적에게 추가 카드, 지배력, 수치 또는 선행 배치 보정을 주지 않는다.
- AI는 모든 합법 행동의 한 수 결과만 평가하며 아래 점수를 합산한다.

| 평가 항목                              | 점수              |
| -------------------------------------- | ----------------- |
| 상대 리더 즉시 패배                    | `+100000`         |
| 자기 리더 즉시 패배                    | `-100000`         |
| 상대 유닛 파괴                         | 대상당 `+5000`    |
| 상대 리더 유효 피해                    | 피해 1당 `+1000`  |
| 상대 유닛 유효 피해                    | 피해 1당 `+250`   |
| 합법 `PLACE`                           | `+400`            |
| `PLACE` 후 예상 지배력 증가            | 지배력 1당 `+100` |
| 배치 카드의 Cost                       | Cost 1당 `+50`    |
| 다음 공격 또는 배치 경로를 여는 `MOVE` | `+300`            |
| `DRAW`                                 | `+200`            |
| `DISCARD`                              | `+50`             |
| `END_TURN`                             | `0`               |

- 동점은 Action 종류 문자열, Field index, 카드 정의 ID의 오름차순으로 결정한다.
- Stage 실행 시 서버가 시드를 발급하며 같은 상태와 시드는 같은 AI 결정을 만들어야 한다.

### 게이트 F — 전투 프레젠테이션과 SFX

#### 재생 정책과 시간

- 기본 재생 속도는 `1x`이며 `2x`, `4x`와 현재 Action 전체 `Skip`을 제공한다.
- 아래 값은 `1x` 기준이고 Tween, Animation, wait와 timeout은 Action 시작 시 캡처한 속도
  배율로 나눈다.

| 연출             |  시간 |
| ---------------- | ----: |
| 공격자 접근      | 160ms |
| 공격 impact      | 120ms |
| 공격자 복귀      | 160ms |
| 피해 flash·shake | 180ms |
| 사망·fade        | 360ms |
| 회복             | 300ms |
| 드로우           | 220ms |
| 이동             | 260ms |
| 배치             | 300ms |
| 버리기           | 220ms |
| 수치 변경        | 200ms |
| 상태 추가·제거   | 240ms |

- 이동과 접근은 `Cubic.Out`, 복귀는 `Cubic.InOut`, scale·alpha는 `Quad.Out`, shake는
  `Sine.InOut` easing을 사용한다.
- 규칙상 동시 피해와 동시 파괴만 병렬 재생하며 나머지 Effect와 Trigger cue는 순차 재생한다.
- cue 하나의 timeout은 `1x` 기준 1500ms, Action 전체 안전 timeout은 15000ms로 두고 재생
  속도에 맞춰 줄인다.

#### SFX

- 기본 SFX 음량은 `0.8`, 초기 음소거는 `false`이며 Sound 완료는 상태 반영을 차단하지 않는다.
- 자산 키는 `sfx.battle.*` prefix로 고정하고 최소한 `attack`, `impact`, `damage`, `destroy`,
  `heal`, `draw`, `move`, `place`, `discard`, `stat`, `status.add`, `status.remove`를 제공한다.
- 브라우저 호환을 위해 OGG와 MP3 fallback을 함께 제공한다.
- SFX는 자체 제작 또는 CC0 자산만 사용하며 출처 URL, 제작자, 라이선스와 취득일을 기록한다.
- v1에는 BGM, 음성, 별도의 reduced-motion 전용 Animation을 추가하지 않는다.

```text

  -> BattleSession
```

### AI 행동 결정

AI는 현재 상태에서 모든 합법 행동을 생성하고 다음 우선순위로 점수를 부여한다.

1. 상대 리더를 즉시 패배시키는 행동
2. 상대 유닛을 파괴하면서 자기 카드를 보존하는 공격 또는 Skill
3. 상대 리더 또는 유닛에 주는 유효 피해
4. 비용과 지배력 효율이 높은 합법 PLACE
5. 다음 공격 또는 PLACE 경로를 여는 MOVE
6. 필요한 DRAW 또는 DISCARD
7. 실행할 가치가 있는 행동이 없을 때 `END_TURN`

동점은 행동 종류, 필드 인덱스, 카드 정의 ID 순으로 결정해 같은 입력 상태에서 항상 같은 행동을
선택한다. 정확한 계산에는 게이트 D에서 승인된 점수와 동점 규칙을 사용한다.

### Action 해결 결과 계약

시뮬레이션은 Phaser 연출 완료를 기다리지 않고 Action 전체를 동기식으로 계산하되, 화면이 원자적
Effect 순서를 재생할 수 있는 결과를 함께 반환한다.

| 계약               | 책임                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| `ActionResolution` | Action 시작 상태, 최종 상태와 순서가 보존된 `ResolutionStep` 목록     |
| `ResolutionStep`   | 원자적 Effect ID, `beforeState`, `afterState`, 의미 기반 전투 이벤트  |
| `BattleEvent`      | 대상 카드·플레이어 인스턴스 ID와 DAMAGE, MOVE, DESTROY 같은 규칙 결과 |

`BattleEvent`에는 Phaser 객체, Animation 키, Sound 키, Tween 시간이나 easing을 넣지 않는다.
동일 시뮬레이션 결과는 화면 연출 유무와 관계없이 같은 최종 상태를 만들어야 한다.

| `Done when`   | 어떤 검증을 통과해야 완료인가?               | 치명 피해 카드가 피격·사망 Animation보다 먼저 사라지지 않고, 다중 Effect와 Trigger 연쇄가 원래 순서로 표시되어야 한다. 동시 사망은 함께 연출된 뒤 함께 제거되어야 한다. `1x`, `2x`, `4x`, Skip의 최종 전투 상태가 같고, 재생 중 추가 입력과 AI 행동이 차단되어야 한다. 음소거, 브라우저 오디오 차단, 누락 자산, timeout, Scene shutdown 뒤에도 다음 상태로 진행하며 중복 callback, 살아 있는 Tween, Sound나 임시 view가 남지 않아야 한다.                                                                                               |

### 프레젠테이션 계약

Phase 5의 의미 기반 `BattleEvent`는 Phaser 전용 adapter에서 다음 cue로 변환한다.

| Cue 종류    | 책임                                                         | 상태 반영 차단 |
| ----------- | ------------------------------------------------------------ | -------------- |
| `ANIMATION` | spritesheet 또는 atlas 기반 등장, 공격, 피격, 사망 Animation | 설정 가능      |
| `TWEEN`     | 카드 이동, 확대·축소, alpha, 흔들림, 수치 배지 변화          | 설정 가능      |
| `SOUND`     | 공격, 피해, 회복, 드로우, 배치, 파괴와 상태 SFX              | 차단하지 않음  |
| `VISUAL_FX` | 파티클, 섬광, 피해 팝업, 카메라 효과                         | 설정 가능      |

`BattlePresentationController`는 cue 변환 결과의 재생, 입력 잠금, 속도, Skip, timeout과
cleanup을 소유한다. Phaser Animation 자산이 필요한 경우 자산 매니페스트에 `spritesheet`와
`atlas` variant를 추가하고 `BootScene`이 안정적인 키와 frame config로 로드하게 한다.

### Effect별 화면 반영 순서

```text
Action 입력
  -> simulation이 ActionResolution 계산
  -> 사용자 입력과 AI 잠금
  -> ResolutionStep 순회
       -> beforeState에 존재하는 제거 예정 GameObject 보존
       -> BattleEvent를 PresentationCue로 변환
       -> 순차 또는 명시적 병렬 cue 재생
       -> blocking cue 완료 또는 timeout
       -> afterState 화면 반영
       -> 임시 GameObject 정리
  -> 최종 화면과 ActionResolution.finalState 일치 확인
  -> 승패 연출 또는 다음 입력 해제
```

시뮬레이션은 최종 상태를 미리 계산할 수 있지만 다음 입력, AI, 보상 요청과 결과 화면 전환은
마지막 프레젠테이션 barrier를 통과하기 전에는 시작하지 않는다.

### Effect와 기본 연출

| 규칙 결과                     | Animation·Tween·Visual FX                            | Sound          | 상태 반영 시점                            |
| ----------------------------- | ---------------------------------------------------- | -------------- | ----------------------------------------- |
| ATTACK 기본 전투              | 공격자 이동 → impact → 동시 DAMAGE → 복귀            | 공격, impact   | 각 DAMAGE step의 blocking 연출 후         |
| `DAMAGE`                      | 대상 flash·shake, 피해 수치, 치명 피해 시 death·fade | 피해, 파괴     | death 연출 완료 후 Field 제거와 Drop 반영 |
| `HEAL`                        | 발광, 회복 수치와 HP 배지 Tween                      | 회복           | 회복 연출 후 HP 반영                      |
| `DRAW`                        | Deck에서 Hand로 카드 이동·확대 Tween                 | 드로우         | 카드 이동 후 Hand 반영                    |
| `MOVE`                        | 출발 Field에서 도착 Field까지 위치 Tween             | 이동           | 도착 후 위치 반영                         |
| `PLACE`                       | 출발 존에서 Field로 이동, 등장 Animation             | 배치           | 등장 완료 후 Field 반영                   |
| `DESTROY`                     | 대상 view 보존, 파괴 Animation과 fade                | 파괴           | 완료 후 view 제거와 Drop 반영             |
| `DISCARD`                     | Hand에서 `afterState`가 지정한 존으로 이동           | 버리기         | 이동 후 대상 존 반영                      |
| `MODIFY_STAT`                 | 대상 배지 pulse와 숫자 Tween                         | 수치 변경      | Tween 후 유효 수치 반영                   |
| `ADD_STATUS`, `REMOVE_STATUS` | 상태 아이콘 진입·퇴장 Animation과 강조 FX            | 상태 추가·제거 | 아이콘 연출 후 상태 반영                  |

동시 피해·파괴 대상은 같은 `ResolutionStep`의 병렬 cue 그룹으로 실행하고, 그룹의 모든 blocking
cue가 끝난 다음 한 번에 `afterState`를 반영한다.

### 사망 카드 view 수명주기

1. `beforeState`에는 있지만 `afterState`의 Field에는 없는 대상 view를 식별한다.
2. Field 전체 재렌더 전에 실제 카드 컨테이너를 별도 효과 레이어로 옮겨 보존한다.
3. 보존한 view를 대상으로 피격, death Animation, Tween과 SFX를 실행한다.
4. blocking 연출이 끝난 뒤 `afterState`를 렌더링하고 Drop 최신 카드 표시를 갱신한다.
5. 보존한 view와 관련 listener를 정확히 한 번 제거한다.

ID만 보존하고 실제 GameObject를 Field 레이어에 남기면 전체 재렌더의 `removeAll(true)`에 의해
먼저 파괴될 수 있으므로 허용하지 않는다.

### 재생 속도와 Skip

- 전역 재생 속도는 `1x`, `2x`, `4x`만 허용한다.
- Action 시작 시 속도를 캡처하고 같은 Action의 Tween, Animation, wait와 timeout에 동일하게
  적용한다. 재생 도중 변경한 값은 다음 Action부터 사용한다.
- SFX는 음높이 왜곡을 피하기 위해 1x로 재생하고 cue 발생 시점만 속도에 맞춘다.
- Skip은 현재 Effect만이 아니라 현재 Action의 남은 연출 전체를 대상으로 한다.
- Skip 요청은 진행 중인 Tween·Animation·timer와 임시 SFX를 중지하고, 남은 `afterState`를
  순서대로 정확히 한 번 적용한 뒤 최종 상태를 렌더링한다.
- Skip 처리 중에는 새 SFX나 Visual FX를 시작하지 않고 완료 후 다음 입력을 해제한다.

### 전투 SFX

- 공격, impact, 피해, 회복, 드로우, 이동, 배치, 파괴, 버리기, 수치 변경, 상태 추가·제거에
  안정적인 SFX 자산 키를 정의한다.
- Sound 자산은 게이트 F에서 승인된 자체 제작 또는 CC0 출처만 사용하고 라이선스 기록을 남긴다.
- 전체 SFX 음량과 음소거는 세이브 슬롯의 게임 규칙 상태가 아닌 로컬 클라이언트 설정으로
  보관한다.
- 첫 사용자 제스처에서 브라우저 AudioContext 활성화를 시도하고, 차단되면 조용히 전투를
  계속하되 진단 가능한 상태만 기록한다.
- SFX 완료는 상태 반영 barrier가 아니며 긴 Sound가 다음 Action을 지연시키지 않는다.

### 실패와 정리

- Animation, Tween과 Visual FX에는 속도 배율이 적용된 최대 timeout을 둔다.
- cue 자산이 없거나 재생 오류가 발생하면 자산 키, step ID와 오류를 기록하고 해당 cue를
  완료 처리한다.
- timeout 또는 오류 뒤에도 해당 `afterState`를 적용하고 다음 step으로 진행한다.
- Scene shutdown에서는 pending Promise를 취소 상태로 만들고 timer, Tween, Animation listener,
  Sound와 보존 view를 제거한다.
- Scene을 다시 열면 남은 연출을 재개하지 않고 시뮬레이션의 권위 상태를 새로 렌더링한다.

| `Context`     | 어떤 파일·오류·문서·기존 구현을 봐야 하는가? | 모든 이전 Phase의 Schema, API, simulation, 전투 프레젠테이션, Scene, UI, 자산 매니페스트, 저장 마이그레이션과 테스트 결과를 함께 확인한다.                                                                                                                                                                      |
| `Constraints` | 무엇을 지키고 무엇을 변경하면 안 되는가?     | 테스트를 통과시키기 위해 규칙을 완화하거나 `any`, 무근거 assertion, `@ts-ignore`, Scene-local 스타일, 하드코딩 Stage를 추가하지 않는다. `dist/`, `artifacts/`, 임시 이미지와 진단 코드를 남기지 않는다. 게이트 E가 동결한 v1 범위를 넘어 서버 권위 전투, PvP, 추가 Stage와 새 규칙을 구현하려면 재승인한다.     |
| `Done when`   | 어떤 검증을 통과해야 완료인가?               | 단위·Schema·API·프레젠테이션·통합·Playwright 테스트와 `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, `npm run build`, `git diff --check`가 모두 통과해야 한다. 가로·세로 화면에서 `1x`, `2x`, `4x`, Skip, 음소거를 수동 확인하고 남은 warning과 미실시 항목을 완료 보고서에 명시한다. |

### 필수 종단 간 시나리오

1. 사용자 A가 가입하고 로그인하면 빈 세이브 슬롯 3개가 보인다.
2. 슬롯 1에서 새 게임을 만들면 아군 카드 30장과 합법 starter 덱이 생성된다.
3. Stage 화면에서 덱 구성 화면을 열고 카드와 리더를 변경한 뒤 저장할 수 있다.
4. 30장 미만 또는 31장 이상, 리더 누락, 같은 유닛 3장인 덱으로는 Stage를 시작할 수 없다.
5. 합법 덱으로 Stage 01을 시작하면 저장 덱과 독립된 전투 덱이 생성된다.
6. 전투 중 카드가 피해를 받거나 Drop/Exile로 이동해도 저장 덱은 변하지 않는다.
7. 치명 피해를 받은 카드는 피격·사망 연출이 끝날 때까지 화면에 남고 그 후 Drop으로 이동한다.
8. 다중 Effect와 Reactive 연쇄는 Effect별로 연출하고 상태를 같은 순서로 반영한다.
9. 여러 카드가 동시에 파괴되면 병렬로 연출한 뒤 모두 함께 제거한다.
10. 전투 연출 중 사용자 입력과 AI 다음 행동이 실행되지 않는다.
11. 같은 Action을 `1x`, `2x`, `4x`와 Skip으로 처리해도 최종 상태가 같다.
12. 음소거, 오디오 차단, 누락 자산과 timeout 뒤에도 전투가 계속된다.
13. Stage 01의 마지막 승리 연출 후 적 카드가 정확히 1장 지급되고 슬롯 컬렉션에 남는다.
14. 동일 완료 요청을 반복해도 보상은 중복 지급되지 않는다.
15. 재로그인과 서버 재시작 후 슬롯, 덱, 진행도와 획득 카드가 복원된다.
16. 획득한 적 리더를 덱의 리더로 교체해 다시 Stage 01을 시작할 수 있다.
17. 사용자 B는 사용자 A의 슬롯, 덱과 컬렉션을 조회하거나 수정할 수 없다.
18. 새 Deck과 Stage fixture를 추가했을 때 기존 Scene 코드 변경 없이 목록과 전투 진입에
    반영된다.

## 6. 완료 보고 원칙

각 Phase 완료 보고에는 다음 내용을 포함한다.

- 실제 변경 파일
- 사용자 승인 결정과 적용 결과
- 실행한 검증 명령과 결과
- 생성한 이미지의 프롬프트 버전, 최종 경로와 실패 로그
- 남은 warning, 실패, 미실시 수동 검증
- 승인 범위 이탈로 재승인이 필요한 항목

검증 실패, 이미지 실패, 미실시 시각 확인을 성공으로 보고하지 않는다.
